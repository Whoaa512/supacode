# K1 — Task chord vs tab chord: implementation brief

Read on cj-main at `2579bcf4` (S1 + S1 r1 landed). Nothing here was compiled or
run; every "today" statement is from reading source. Claims marked
**(unproven)** are races inferred from the code, to be confirmed by the
failing-first test before the fix is written. If such a test passes on
unmodified code, drop that change and record it in Progress.

Scope in one line: the task chord already steps one task per press (S1); K1
makes it correct under key repeat and unable to mint, points the tab chord at
the selected task, and pins A25's task and tab halves with tests. No new
chord, no new state field, no view change, no persistence change.

## 1. What exists today

Task chord (Select Next / Select Previous, Sessions tab active):

- `WorktreeCommands.swift`: the two buttons send
  `.repositories(.selectNextWorktree | .selectPreviousWorktree)`. They do
  **not** drop auto-repeat events (the tab buttons do), so a held chord sends
  one action per repeat.
- `AppFeature.body` runs `core` **before** `Scope(\.repositories)`. `core`'s
  arm `case .repositories(.selectNextWorktree), .repositories(.selectPreviousWorktree)`
  overwrites the row selection with `AppFeature.focusedSessionRowID(state:)`
  when that is non-nil. That function answers `.task(terminals.selectedLayoutID)`
  when the selected layout has a focused surface and a task row.
- `RepositoriesFeature` `.selectNextWorktree` / `.selectPreviousWorktree` /
  `.selectWorktreeAtHotkeySlot`: on the Sessions tab call
  `focusSessionNavigation(state:id:)` with `state.sessionRowID(byOffset:focusedRowID: nil)`
  / `sessionRowID(atSlot:)` (`SessionsSidebarStructure.swift`). Both walk
  `sessionsSidebarStructure.liveIDs` only.
- `liveIDs` is built in `recomputeSessionsSidebarStructureIfChanged()` from
  rows with `isLive` (`location != nil`). For a `.task` row, `taskDraft` sets
  `location = leading?.location ?? group.tabs?.location`: non-nil iff an
  agent runs on one of the task's surfaces or the task holds a tab. This is
  already the plan's "a task is live if any member or shell surface is live".
  A `.task` row is `.settled` only when `location == nil` (`appendTaskDrafts`),
  so no settled row is ever in `liveIDs`.
- `focusSessionNavigation` → `selectSessionRow(id)` → `focusEffect`: `.task`
  ids send `.delegate(.focusTask(layoutID, directory:))`, other ids
  `.delegate(.focusSession(location))`.
- `AppFeature.focusTask(_:directoryID:state:)` (`AppFeature+Sessions.swift`):
  `.send(.repositories(.selectTask(...)))` then
  `terminalClient.send(.ensureInitialTab(layoutID, context, runSetupScriptIfNew: false, focusing: true))`.
  No guard. `.selectTask` sets `selectedTask` and sends
  `.delegate(.selectedWorktreeChanged(worktree, layoutID:))`, whose handler in
  `AppFeature.swift` sends `.setSelectedLayoutID(layoutID)` and a second
  `.ensureInitialTab(...)`.
- `WorktreeTerminalManager.ensureInitialTab(in:context:runSetupScriptIfNew:focusing:)`
  **creates a tab** (`createTabAsync`) when the layout has no panes or does not
  exist. It is the only minting path the chord can reach.
- `terminals.selectedLayoutID` changes only when the manager handles
  `.setSelectedLayoutID` and echoes `TerminalsFeature.Action.selectedLayoutChanged`,
  i.e. at least one async effect hop after the key press.
- `AppFeature.syncSessionSelectionToFocus(state:)` runs on every `.terminals`
  action and moves the row selection to the focused row when that differs
  from `state.lastFocusedSessionRowID`.
- `RepositoriesFeature.State.selectedTaskID` / `orphanTaskID`
  (`SessionsSidebarStructure.swift`), `AppFeature.State.shownTask(forDirectory:)`,
  `taskOnMissingDirectory`, `AppFeature.hasTask`, `AppFeature.storedTask`
  (`AppFeature.swift`, `AppFeature+Sessions.swift`).

Tab chord:

- `TerminalCommands.swift` `TerminalTabSelectionItems`: sends
  `.selectPreviousTerminalTab` / `.selectNextTerminalTab` (auto-repeat dropped
  in `RelativeTabSelectionButton`) and `.selectTerminalTabAtIndex(n)`.
- `AppFeature.swift` arms `.selectNextTerminalTab`, `.selectPreviousTerminalTab`,
  `.selectTerminalTabAtIndex`: each requires a roster worktree for
  `repositories.selectedWorktreeID` that is not `isMissing`, then targets

  It never creates or closes anything.

## 2. Design

No new types, state fields, actions or views. Three small changes, all in the
App layer.

### 2a. Cycle origin survives the echo window — `AppFeature+Sessions.swift`

Problem **(unproven)**: press 1 selects task B and sets `selectedTask = B`
synchronously (`.send` chain), but `terminals.selectedLayoutID` is still A
until the echo. A second press inside that window hits `core`'s arm, which
resets the selection to `.task(A)`, and the offset lands on B again: a held
chord stalls instead of advancing.

Add, next to `focusedSessionRowID`:

```swift
/// Where the task chord steps from: the task last asked for, since the
/// terminal echoes a selection after the press that made it; else the
/// focused row.
static func sessionCycleOrigin(state: State) -> SessionRowID? {
  if let asked = state.repositories.selectedTaskID,
    let row = state.repositories.sessionItems[id: .task(asked)]?.id
  { return row }
  return focusedSessionRowID(state: state)
}
```

In `AppFeature.swift`, the `core` arm for
`.repositories(.selectNextWorktree), .repositories(.selectPreviousWorktree)`
calls `sessionCycleOrigin` in place of `focusedSessionRowID`. Nothing else in
the arm changes (still gated on `isSessionsSidebarTabActive`, still a nil
origin leaves the stored selection alone).

Why `selectedTaskID` is safe as origin: it is written only by `.selectTask`,
cleared by `.selectedTaskRemoved`, by the `selectedWorktreeChanged` handler
when a directory selection resolves to another task, and by leaving the
directory (computed). So it is nil or the layout last sent to the terminal.
If it were ever stale the cost is one press stepping from the wrong row,
after which `.selectTask` rewrites it.

Do not touch `handleNextSessionNeedsMe`, `handleSettleSessionAndAdvance` or
`handleUnsettleCurrentSession` (K2 / T9 own them); note in Progress that K2
should use `sessionCycleOrigin` too.

### 2b. The highlight does not bounce back during repeat — `AppFeature+Sessions.swift`

Problem **(unproven)**: presses A→B→C; the echo for B arrives after the
selection is already C; `syncSessionSelectionToFocus` sees focused row B ≠
`lastFocusedSessionRowID` (A) and moves the highlight back to B until C's
echo. Visible flicker (A33).

In `syncSessionSelectionToFocus`, after the existing "row does not exist yet"
return and before the `lastFocusedSessionRowID` comparison:

```swift
// A task was asked for and the terminal has not shown it yet: the focus
// seen now is the one being left.
if let asked = state.repositories.selectedTaskID,
  asked != state.terminals.selectedLayoutID,
  state.repositories.sessionItems[id: .task(asked)] != nil,
  hasTask(asked, state: state)
{ return }
```

Return without writing `lastFocusedSessionRowID`, so the echo for `asked`
still records and (re)selects it. The `hasTask` and row checks bound the
hold: a removed task releases it at once (and `.selectedTaskRemoved` follows
from `sessionsLinkReducer`).

### 2c. Cycling cannot mint — `AppFeature+Sessions.swift`

`focusTask` decides on the terminal state at the time it runs, not on the
sidebar row (the row is built from a snapshot that can be one pass behind):

```swift
static func focusTask(_ layoutID: LayoutID, directoryID: Worktree.ID, state: State) -> Effect<Action> {
  // The row may outlive the task's last tab by one snapshot; showing an
  // emptied task would bootstrap a shell tab in it.
  guard taskHoldsTabs(layoutID, state: state) else { return .none }
  ... unchanged ...
}

/// Whether the task holds a tab on any pane: by its layout once it has one
/// this run, else by its stored record.
static func taskHoldsTabs(_ layoutID: LayoutID, state: State) -> Bool {
  if let live = state.terminals.layouts[id: layoutID] {
    return live.layout.panes.contains { !$0.tabs.isEmpty }
  }
  return storedTask(layoutID, state: state)?.layout.panes.contains { !$0.tabs.isEmpty } == true
}
```

Do not reuse the existing `taskHoldsTabs(_:onDirectory:state:)`: it also
requires the directory to match, and a row's `location.directoryID` is not
proven equal to the task's directory for every row kind. Keep both; the new
one is the directory-free half (the old one may call it if that is a clean
edit, otherwise leave the old one alone).

A refused `focusTask` sends nothing: no `.selectTask`, no terminal command.
`focusSessionNavigation` has already moved `sessionSelection` to the row;
leave that (the next `taskSnapshotsChanged` drops the row and
`reconcileSessionItems` clears the selection). Do not make the chord skip
ahead to another row.

This guard also covers row clicks on a live task row (`.activateSession` →
`focusEffect` → `.focusTask`). That is intended: a click must not mint
either (D2). A dormant row never reaches `focusTask` (it resumes).

Not changed: `ensureInitialTab` in the manager, the `selectedWorktreeChanged`
handler, `focusSession` (uses `terminalClient.focusSurface`, which targets an
existing surface).

### 2d. Tab chord targets the selected task — `AppFeature.swift`

Add to `AppFeature.State`, beside `shownTask(forDirectory:)`:

```swift
/// The layout the tab-selection chords act on: the task on screen. A task
/// on a directory outside the roster or gone from disk is still on screen.
var tabChordLayoutID: LayoutID? {
  if let orphan = repositories.orphanTaskID {
    return AppFeature.hasTask(orphan, state: self) ? orphan : nil
  }
  if let shown = taskOnMissingDirectory { return shown }
  guard let worktree = repositories.worktree(for: repositories.selectedWorktreeID), !worktree.isMissing
  else { return nil }
  return shownTask(forDirectory: worktree.id) ?? layoutID(forDirectory: worktree.id)
}
```

The three arms `.selectTerminalTabAtIndex`, `.selectNextTerminalTab`,
`.selectPreviousTerminalTab` become:

```swift
guard let layoutID = state.tabChordLayoutID else { return .none }
return .run { _ in await terminalClient.send(.selectRelativeTab(layoutID, forward: true)) }
```

(same shape for the other two; command payloads unchanged). The trailing
`?? layoutID(forDirectory:)` keeps today's target for a directory with no
shown task, so `AppFeatureSelectTerminalTabTests` passes unmodified (the
manager no-ops on a layout with no tabs).

What this fixes: (1) in the echo window after a task switch the chord acted
on the task just left (`shownTask` prefers `selectedTask`); (2) dead chord
while an orphan task or a task on a missing directory is shown.

Do not touch any other menu command (`renameSelectedTerminalTab`, split,
close, search, new tab): Z1 owns those sites. No change to
`TerminalCommands.swift` or `WorktreeTerminalManager.selectRelativeTab`.

## 3. Destructive and persistence paths

K1 adds none. Rules for the implementer:

- No sidecar write, no `TaskRecord`/membership write, no layouts-file write
  is added. The only persistence a press causes is the existing
  `TerminalsFeature` `selectedLayoutChanged` → `recordActiveTask`; leave it.
- The chord must never send `.createTab`, `.createTabWithInput`,
  `.destroyTab`, `.destroySurface`, `.closeFocusedTab`, `.closeFocusedSurface`,
  `.closePane`, or `.delegate(.resumeSession)`, and never set
  `pendingSessionLaunch`. The §2c guard is the only place a decision is made,
  and it reads current `state.terminals` / the stored record, positively: an
  unknown layout with no record is "holds no tab" → do nothing.
- No ordered list is written. `liveIDs`, `taskSessions`, `subRows` order are
  read only. Do not re-sort `liveIDs` or add a second ordering.
- No timer, clock or debounce is added. Nothing is closed, killed or
  settled by K1.

## 4. Edge cases and races

| Case | Required behaviour |
|---|---|
| Two presses before the first echo | Second press steps from the task asked for by the first (§2a). |
| Echo for an intermediate task arrives after a later press | Highlight stays on the latest asked task (§2b). |
| Row live in the sidebar, task's last tab already gone | `focusTask` returns `.none`; no command, `selectedTask` unchanged (§2c). |
| Tab closes between the reducer guard and the manager handling `ensureInitialTab` | Not closed by K1 (manager unchanged). Accepted; record in Progress as a residual for whoever next edits `ensureInitialTab` (a non-bootstrapping "show" command). |
| Never-opened task (record only, has tabs) | Reachable by the chord as today (A36); guard passes via the stored record. |
| Dormant or settled task; implicit history row | Not in `liveIDs`; chord skips it; nothing resumes. |
| Task with open tabs whose agents all ended | Live (tabs), visited; no resume. |
| Task with two agents | One stop per lap, not two. Chord shows the task with its own focus (`focusTask`), not the most urgent member's surface (that is K2). |
| Selection on a dormant row via arrow keys, then chord | Steps from `sessionCycleOrigin` (asked task, else focused row); if neither, first/last live row (existing fallback). |
| One live task | Chord re-shows it; no beep, no mint. |
| No live row | `.none` (existing). |
| Sessions tab not active | Worktree / agents branches unchanged. |
| Orphan task shown | Task chord works (T5 r1); tab chord now works (§2d). |
| Selected task on a missing directory | Tab chord acts on `taskOnMissingDirectory`. |
| Directory selected with no task | Tab chord targets the seam id as today; manager no-ops. |
| Two tasks on one directory, switch then tab chord at once | Acts on the task just selected, not the recorded one. |
| Selected task with one tab, or tabs only in an unfocused pane | Tab chord no-ops / stays in the focused pane (manager, unchanged). Never crosses to another task. |
| Hibernated target tab | `.wakeTab` then `.selectTab` as today; this is a renderer wake, not a spawn. |
| `selectedTask` cleared mid-repeat (`.selectedTaskRemoved`) | Origin falls back to the focused row; hold in §2b releases. |
| Two `.setSelectedLayoutID` effects from consecutive presses delivered out of order | Not addressed (pre-existing, unstructured effects); live-UI item §7. |

## 8. Decisions the plan left open, and contradictions

1. **Tab chord scope stays "tabs of the focused pane"**, not every surface of
   the task. The plan and A25/D7 say "surfaces inside the selected task".
   Kept because the plan also says "the existing tab chord, no new chord",
   changing `selectRelativeTab` to cross panes changes behaviour for every
   split user, and merge flattens into the focused pane while tangents open
   as tabs, so a task's agents are normally tabs of one pane; the pane chord
   (`focusRelativePane`) covers the rest. What K1 guarantees is the half A25
   can fail on: the chord never leaves the selected task. **This narrows the
   plan's wording; cj to confirm or ask for a cross-pane walk as a follow-up.**
2. **The task chord shows the task with its own focus**, not the most urgent
   member's surface (the row's `location`). Follows T5/S1 (`focusTask`);
   exact-surface targeting is K2.
3. **`selectTerminalTabAtIndex` is included** with the two relative arms: same
   three-line resolution, and leaving it on the directory seam would make ⌘n
   and the bracket chords disagree during the echo window. The remaining
   menu sites stay with Z1 as Progress assigns them.
4. **Cycle origin is the task last asked for** (`selectedTaskID`), ahead of
   the focused row. The plan does not mention the echo window.
5. **A stale live row is refused, not skipped.** The chord does nothing for
   that press rather than hunting for the next row; simplest rule that
   cannot mint, and the row is gone one snapshot later.
6. **The guard sits in `focusTask`, so clicks get it too.** Not asked for by
   K1, but a click on a stale row had the same mint.
7. **Manager-side mint in `ensureInitialTab` is left open** (effect-time
   window, §4). Closing it needs a non-bootstrapping show command and touches
   the `selectedWorktreeChanged` handler; out of a keyboard slice.
8. **The task chord keeps accepting auto-repeat** (A33 is judged under key
   repeat); the tab chord keeps dropping it (existing).
9. Contradiction with Progress, not the plan: S1 says "K1: the chord already
   steps one task per press". True per press with the echo landed; §2a/§2b
   are the cases where it does not, both unproven until tests 1 and 2 run red.
10. No follow-up in `task-as-unit-followups.md` names K1; none folded in.
