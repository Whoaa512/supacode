## 2. Design

No change to `SubRow`, to the structure computation, to `TaskMember`, to
membership, or to anything under `Features/Terminal` / `Clients/Terminal`.

### 2.1 Repositories: one action, one delegate

`RepositoriesFeature.Action` (next to `activateSession`):

```swift
case activateSessionSubRow(task: LayoutID, member: TaskMember)
```

`RepositoriesFeature.Delegate` (next to `resumeSession`):

```swift
/// Resume into this task, whatever directory the session ran in.
case resumeSessionInTask(SessionKey, LayoutID)
```

Wiring the compiler will ask for: `Action.cacheInvalidations`
(`SidebarStructure.swift`): add to the list that returns `[]` (beside
`.activateSession`); the no-op session list in the main `RepositoriesFeature`
reducer body (beside `.activateSession`).

Handler in `sessionsReducer`:

```swift
case .activateSessionSubRow(let layoutID, let member):
  let structure = state.sessionsSidebarStructure
  // Current state decides: the click may be older than the list.
  guard structure.subRowsTaskID == layoutID,
    let row = structure.subRows.first(where: { $0.id == member })
  else { return .none }
  if let location = row.location { return .send(.delegate(.focusSession(location))) }
  guard let key = member.sessionKey else { return .none }
  // Dormant here but running in another task: show it there, never start a second copy.
  if let elsewhere = state.sessionSnapshots.first(where: { $0.sessionKey == key })?.location {
    return .send(.delegate(.focusSession(elsewhere)))
  }
  return .send(.delegate(.resumeSessionInTask(key, layoutID)))
```

It writes no state: the selection stays on the task row
(`syncSessionSelectionToFocus` already maps any focused surface of a task to
its `.task` row).

Change in the existing `.activateSession` handler, dormant branch only: a
`.task(layoutID)` row sends `.resumeSessionInTask(key, layoutID)`; an
`.implicit` row keeps `.resumeSession(key)`.

```swift
guard let key = row.sessionKey else { return .none }
if case .task(let layoutID) = id { return .send(.delegate(.resumeSessionInTask(key, layoutID))) }
return .send(.delegate(.resumeSession(key)))
```

### 2.2 App: carry the target task through the resume pipeline

`AppFeature+Sessions.swift`:

- `PendingSessionLaunch` gains `var task: LayoutID?` (nil = today's
  behaviour: reuse by directory or mint).
- `sessionsLinkReducer`: add
  `case .repositories(.delegate(.resumeSessionInTask(let key, let layoutID))): return Self.handleResumeSession(key, task: layoutID, state: &state)`.
- `handleResumeSession(_:task:state:)`: new `task: LayoutID? = nil` parameter,
  stored on the `PendingSessionLaunch` it creates. Cooldown, `prepareResumeSession`
  and the probe are unchanged (the probe still runs at the session's own cwd,
  A38).
- `finishResumeBranchProbe`: the "already live" check prefers the target task:
  `sessionSnapshots.first { $0.sessionKey == key && $0.location.layoutID == pending.task }?.location ?? sessionLocation(for: key)`.
  Nothing else changes; the alert texts stay.
- `startPreparedResume`: it builds a fresh `PendingSessionLaunch`; copy the
  target across first. The guard at its top already proves the stored pending
  is this request or nil.

  ```swift
  let target = state.pendingSessionLaunch?.task   // read before overwriting
  var pending = PendingSessionLaunch(key: …, cwd: …, command: …, requestID: requestID)
  pending.task = target
  if let target, let directory = taskDirectory(target, state: state) {
    pending.launched = true
    state.pendingSessionLaunch = pending
    return launchSessionTab(pending, directory: directory, into: target, state: &state)
  }
  pending.task = nil            // task gone: fall through to today's path
  // … existing worktreeForCwd / registerSessionFolder code, unchanged
  ```

  The confirm path (`confirmBranchMismatchResume`) needs no edit: it leaves
  `state.pendingSessionLaunch` in place and passes its `requestID`.

- New helper, the only place that decides a targeted launch is still valid:

  ```swift
  /// The task's directory, when the task still exists. A removed task is
  /// never launched into: a tab on its id would bring it back.
  static func taskDirectory(_ layoutID: LayoutID, state: State) -> DirectoryContext? {
    guard hasTask(layoutID, state: state),
      let recorded = state.terminals.directories[layoutID] ?? storedTask(layoutID, state: state)?.directory
    else { return nil }
    return directoryContext(forTask: layoutID, directoryID: recorded.worktreeID, state: state)
  }
  ```

- `launchSessionTab(_:directory:into:state:)`: new `into target: LayoutID? = nil`.

  ```swift
  let owner = target ?? (pending.isNewSession ? nil : task(listing: pending.key, onDirectory: …))
  // unchanged: layoutID = owner ?? LayoutID(task: uuid()); primary is nil whenever owner != nil
  let input = target == nil ? pending.command : resumeInput(pending, in: directory)
  ```

  ```swift
  /// A session resumes where it ran. In its task's own directory the
  /// command is sent as is; elsewhere it is preceded by a `cd` there.
  static func resumeInput(_ pending: PendingSessionLaunch, in directory: DirectoryContext) -> String {
    let cwd = pending.cwd.standardizedFileURL.path(percentEncoded: false)
    let home = directory.workingDirectory.standardizedFileURL.path(percentEncoded: false)
    guard cwd != home else { return pending.command }
    return "cd \(ZmxClient.shellQuote(cwd)) && \(pending.command)"
  }
  ```

  A targeted launch never sends `.registerSessionFolder` and never seeds
  `PendingTaskLaunch.primary`. The `pendingTaskLaunches` bookkeeping
  (replace the entry for this layout, mark the others not shown) is the
  existing code, unchanged.

## 3. Destructive and persistence paths

S2 adds no path that kills, closes or settles. Rules for what it touches:

1. **Which task.** A targeted resume goes to the task named by the click and
   to no other. It is re-validated at launch time by `taskDirectory`
   (`hasTask`), after the asynchronous probe and after any alert. Never
   resolve the target by `task(listing:onDirectory:)`, by "the directory's
   active task" or by lowest key.
2. **Never resurrect.** A task removed while the resume waited
   (`removedLayoutIDs`, detached layout) is not launched into; the resume
   falls back to the untargeted path, which mints or reuses as today.
3. **Member order is untouched.** A targeted launch seeds no primary
   (`PendingTaskLaunch.primary == nil`) and sends no `.membersChanged`. When
   the resumed agent reports on its new surface, `TaskMembership.reconciled`
   finds the key already listed and changes nothing; no replacement is named,
   so `TaskMembership.storing` and hydration (`hydratedMembers`) keep the
   stored order. A tangent stays a tangent; the primary stays first, running
   or not.
4. **Sidecar.** The only write is the existing `.launchSessionCompleted`
   unsettle of the resumed key. The primary's mark is never touched by a
   tangent resume. Sub-rows offer no settle.
5. **No timer.** Nothing in S2 is scheduled; the 10 s
   `recentSessionLaunchDate` cooldown only drops a repeat launch.
6. **Layout record.** The new tab is written by the existing incremental
   writer; S2 adds no write path.

## 4. Edge cases and races

| Case | Required behaviour |
|---|---|
| Click on a sub-row after the selection moved to another row | `subRowsTaskID != task` → no effect. |
| Member vanished (no longer running nor indexed) between render and click | Not in `subRows` → no effect. |
| Live sub-row's agent ended before the click was reduced | The row is dormant now: resume it in the task (same as a task row, which also acts on current state). |
| Member dormant in this task, running in another task | Focus it where it runs (`focusSession` selects that task). No second process. |
| Member becomes live while the branch probe runs | `finishResumeBranchProbe` focuses it (target task's surface first); no tab created. |
| Task removed while the probe or alert waits | Untargeted fallback: a task is minted or reused by directory; the removed id is not launched into. |
| Session cwd ≠ task directory (tangent that ran elsewhere, D9) | One tab in the clicked task, context = the task's directory, input `cd '<cwd>' && <resume command>`. No task minted, no `registerSessionFolder`. |
| Session cwd == task directory | Input is exactly the resume command (unchanged text). |
| cwd contains spaces or `'` | Quoted by `ZmxClient.shellQuote`. |
| cwd missing or unreadable | Existing alert from `prepareResumeSession`; no command. |
| Remote task | The local cwd check fails → the existing "not accessible" alert, no command. Unchanged limitation (T8 note), not fixed here. |
| Orphan task (directory not in the roster) | `directoryContext(forTask:)` gives the recorded directory; launch proceeds; no folder registration. |
| Dormant task (record only, no layout), tangent clicked | Tab is created in that task id; when it appears `showLaunchedTaskIfReady` selects it; members stay `[primary, tangent]`; the primary stays dormant (D6: tangents resume on click). |
| Settled task (primary marked, no tabs), tangent clicked | The tangent's own mark is cleared by `.launchSessionCompleted`; the primary's stays. The row is Active while the tab is open (S1 rule) and returns to Settled when it closes. |
| Branch mismatch or provisional conflict | Existing alert. Confirm launches in the **same target task**; Cancel clears `pendingSessionLaunch` and launches nothing. |
| Second click while a launch is pending | `prepareResumeSession` returns nil (existing guard). No second tab. |
| Harness with no resume command | `prepareResumeSession` returns nil; nothing happens (as for a history row). |
| Provisional member (unreported agent) | Always live → `focusSession`. A dormant provisional cannot exist; the `sessionKey` guard covers it. |
| Session led by two tasks, dormant row of the second clicked | Resumes in the clicked task (today: lowest key). |
| Primary whose cwd is not the task directory, dormant task row clicked | Resumes in the task with the `cd` prefix (today: mints a second task). |
| Selected task in the collapsed Settled section | Sub-rows render only when the section is expanded, with their task row. |
| Shell that does not understand `cd … && …` | Not handled; setup scripts already assume POSIX-like initial input. |

## 7. Only the live UI can confirm (cj, A35)

- Sub-rows appear under the selected task only, indented, and vanish when
  another row is selected; the highlight stays on the task row.
- Dormant sub-rows read as dimmed; status glyphs match the task row's.
- Clicking a live sub-row focuses that tab (including one in a pane window);
  clicking a dormant one opens a new tab in the same task and the agent
  resumes; a tangent from another directory visibly `cd`s there first.
- Up/down arrows skip sub-rows; Return still acts on the task row.
- Untagged rows inside a `List(selection:)`: no stray highlight, no selection
  cleared by a sub-row click.
- No flicker or scroll jump when a member's status flips (the structure is
  one observed value, so the list body re-runs on each flip; S1 already pays
  this).
- Tooltips show the real (overridden) tab chords.
- A settled task whose tangent is resumed moves to Active and back to Settled
  when that tab closes.

## 8. Decisions the plan left open, and contradictions

1. **Target task is carried explicitly** (`resumeSessionInTask`), for sub-rows
   and for a dormant task row. Why: A23 says "in the same task";
   `task(listing:onDirectory:)` picks by directory and lowest key, which is
   wrong when two tasks list the session or the session ran elsewhere.
   Contradicts the S1 Progress note "dormant → `resumeSession`, which reuses
   the task when it sits on the session's directory": that note described the
   limitation, this closes it. `.implicit` rows are untouched.
2. **`cd` prefix, not a new `workingDirectory` parameter on
   `createTabWithInput`.** Why: no terminal-layer change in a view slice, no
   edit to ~14 test patterns that destructure the command, and it also works
   on a remote host where a local working directory is ignored. Cost: it is
   shell text (as setup-script input already is). Applied only when the cwd
   differs from the task directory, so existing input assertions hold.
   Not fixed here, pre-existing: a same-directory resume into a task whose
   focused tab has `cd`ed away starts in the inherited pwd. Record it in
   `task-as-unit-followups.md` when S2 lands.
3. **No settle on a sub-row.** The S1 Progress "left for S2: per-sub-row
   settle" contradicts D6 ("settle is task-level only"); D6 wins. A tangent
   is closed with Cmd-W. This also avoids the T9 r1 double-alert case. M3 adds
   the sub-row menu (Detach).
4. **Sub-rows are not list selections.** Keyboard reach is the existing tab
   chord (K1) and jump-to-attention (K2); adding sub-row ids to
   `SessionRowID` would touch every selection path S1 just settled.
5. **A tangent resume does not unsettle or resume the primary** (D6:
   reopening resumes the primary; tangents resume on click). The task shows
   as Active through S1's "has a tab" rule.
6. **Running elsewhere wins over resuming here**: a member live in another
   task is focused there. One process per session.
7. **Stale click on a row that just went dormant resumes it.** Same rule as
   the task row; carrying the expected liveness in the action was judged not
   worth a second code path.
8. **`SubRow` gets no cwd or branch field.** A tangent's directory is not
   shown on its sub-row; add it only if cj asks after the UI check.
9. **Remote tasks**: sub-row resume is refused by the existing local cwd
   check. Unchanged from history rows; listed in T8's "left for later".
